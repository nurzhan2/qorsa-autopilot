# Qorsa Autopilot — карта проекта

Локальный оркестратор фриланс-заказов: Google-таблица → задачи → Claude Code в
headless → приёмка → сообщение. Один asyncio-процесс + SQLite, больше ничего.

Файл описывает то, что код **делает сейчас**, а не то, что задумывалось.
Если правишь поведение — правь и этот файл.

---

## Три роли

Автопилот замещает ровно одного участника из трёх. Это главное архитектурное
ограничение, из него растут маршрутизация сообщений и гейты планировщика.

| роль         | за что отвечает                                        | замещает ли бот |
|--------------|--------------------------------------------------------|-----------------|
| **МЕНЕДЖЕР** | берёт заказы, цена, сроки, объём, таблица               | нет, никогда    |
| **ВЛАДЕЛЕЦ** | техчасть: доступы, ключи, технические уточнения          | **да, его**     |
| **КЛИЕНТ**   | даёт доступы, отвечает на технические вопросы            | —               |

Google-таблица — инструмент менеджера и вход системы. Бот из неё читает и
пишет только в свои колонки.

## Запуск

```bash
python -m venv .venv && .venv/Scripts/activate     # на *nix — source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
cp .env.example .env                                # ANTHROPIC_API_KEY, SHEET_ID, VAULT_KEY
python -m autopilot.main
```

Тесты:

```bash
pytest
```

Планировщик вживую, без таблицы, без Telegram и без трат:

```bash
python scripts/seed_demo.py
DRY_RUN=1 python -m autopilot.main
```

`DRY_RUN=1` подменяет `Executor` и `Verifier` заглушками из `autopilot/fakes.py`.
Без него демо попытается запустить настоящий `claude`, и если бинаря нет —
каждая задача упадёт с `ERROR ... не нашёл claude-бинарь`. Это не баг, это
отсутствие CLI.

Секреты:

```bash
python scripts/vault_cli.py genkey        # ключ для VAULT_KEY в .env
python scripts/vault_cli.py add FTP_PASS  # значение спросит, не отображая

```

**Схема БД менялась в фазе 1.** Миграций нет — старый `autopilot.db` надо удалить.

## Маршрутизация сообщений

`communicator.route(text)` даёт один из трёх исходов. Порядок проверок и есть
приоритет: сначала менеджерская сеть, потом владелец, потом клиент.

| исход            | что туда попадает                                                        | как уходит |
|------------------|--------------------------------------------------------------------------|------------|
| `to_manager`     | цена, оплата, скидки, договор, **сроки**, объём, доработки, претензии, отказ, гарантии — и **всё, в чём есть сомнение** | сразу менеджеру, клиенту не отвечаем |
| `to_owner`       | доступ не работает, ошибка/таймаут/403, истёкший ключ, техническая неоднозначность, нераспознаваемое сообщение (стикер, одни эмодзи, пустота) | сразу владельцу |
| `to_client_auto` | запрос доступа по чеклисту, подтверждение получения, «готово, посмотри превью» | клиенту сам, с человеческой паузой 40–900 с |

Сеть на `to_manager` **намеренно широкая**, и правило по умолчанию —
`to_manager`. Осмысленный текст, не попавший ни в одну категорию, уходит
менеджеру. Ложное срабатывание стоит одного лишнего уведомления, пропуск стоит
обязательства, которого никто не давал.

На `to_manager` бот **не отвечает клиенту и не смягчает** — просто пересылает и
замолкает. Это `Communicator.incoming()`.

Адресаты: `to_client_auto` → `Project.tg_chat_id`, `to_owner` →
`TG_OWNER_CHAT_ID`, `to_manager` → `TG_MANAGER_CHAT_ID`. Если внутренний чат не
настроен, сообщение всё равно «отправляется» на символический адрес
`OWNER`/`MANAGER` и попадает в лог — терять уведомление хуже, чем не доставить.

Две вспомогательные функции, чтобы не путать:

* `route(text)` — для целого сообщения, включает правило «при сомнении — менеджеру»;
* `escalation(text)` — для **куска**, дописываемого к готовому сообщению; правила
  по умолчанию не применяет, иначе заголовок задачи «шаг 2» уводил бы к
  менеджеру весь накопленный отчёт о готовности.

Тихие часы (`QUIET_START`/`QUIET_END`, локальное время) держат только
`to_client_auto`. Владельца и менеджера будим когда надо.

### Агрегация отчётов

`on_task_done` не создаёт письмо на задачу. Он дописывает строку в **единственное
неотправленное** сообщение вида `task_done`, а новое заводит только когда прошлое
уже ушло — и не раньше чем через `AGGREGATE_WINDOW_MIN` (по умолчанию 60) после
отправки предыдущего. Закрытие этапа (`active → review`) выталкивает накопленное
немедленно, не дожидаясь окна.

На демо это 3 сообщения за две минуты вместо 80 до фазы 1.

## Полосы и WFQ

| полоса   | лимит | эксклюзивная | гейты | что делает                              |
|----------|-------|--------------|-------|-----------------------------------------|
| `chat`   | 8     | нет          | нет   | `Communicator.process` — переписка       |
| `build`  | 3     | да           | **да**| `Executor.run` — Claude Code в headless  |
| `verify` | 2     | да           | нет   | `Verifier.run` — приёмка                 |

**Эксклюзивная** = один проект не держит два слота этой полосы одновременно.
`chat` не эксклюзивная нарочно: переписка не должна ждать за компиляцией.
Занятые слоты считаются в `Scheduler.running[lane]` — приватное `sem._value`
убрано вместе с семафором.

Один тик занимает не больше, чем свободно на его начало (`quota` в `_dispatch`).

`_pick()` берёт проект с минимальным `служба / weight`, внутри проекта — задачу
с минимальным `order_idx`.

```
weight = {1: 3.0, 2: 2.0, 3: 1.0}[priority] × 4.0 (дедлайн просрочен)
                                            × 2.0 (до дедлайна ≤ 3 дней)

служба = served_units × 0.5 ^ (часов с served_at / SERVED_HALFLIFE_H)
```

`served_units` списывается **в момент выдачи слота** (`DISPATCH_UNITS = 1.0`),
иначе проект с 40 задачами забирал бы все свободные слоты одного тика. По
завершении добивается только превышение: `max(минут − 1.0, 0)`.

Счётчик **затухает экспоненциально** (`db.decayed_units`, период полураспада
`SERVED_HALFLIFE_H`, по умолчанию 24 ч). Без затухания проект, простоявший
месяц, возвращался бы в очередь вечным должником и проигрывал новичкам.

### Захват задачи

`_pick()` возвращает кандидата, право на работу выдаёт `_claim()` — один
условный `UPDATE tasks SET status='running' WHERE id=? AND status='ready'`.
Иначе задача уезжает в работу дважды: `_pick` фильтрует свежий `inflight` по
снимку из БД, снятому чуть раньше, и в окне между запросом и фильтрацией задача
успевает доработать, выйти из `inflight` и быть выданной второй раз. Ловилось
на тесте приоритетов: 336 запусков на 240 задач.

## Два гейта полосы build

Полоса `build` требует двух разрешений от живых людей. Ни одно из них бот
поставить себе не может.

**1. Галочка менеджера «Готов к работе».** Колонка в таблице, поле
`Project.ready_for_work`. Пока не `TRUE`, проект не выходит из `briefing`:
`_pick` для build фильтрует по `ready_for_work is True`. Переписка в `chat` при
этом идёт — брифинг для того и нужен.

**2. Полный чеклист доступов.** Пока хоть один `AccessItem` не в статусе
`verified`, build-слот не выдаётся.

### Жизненный цикл доступа

```
needed -> requested -> received -> verified
                  \-> failed
```

* `needed` — знаем, что нужен, ещё не спрашивали
* `requested` — попросили у клиента (`requested_at`)
* `received` — клиент прислал, значение легло в vault, в БД — только `secret_ref`
* `verified` — доступ проверен и работает (`verified_at`). **Только этот статус открывает build**
* `failed` — прислали, не работает. Маршрут `to_owner`, разбирается владелец

Планировщик держит согласованность в `_sync_access()` на каждом тике:

* есть незакрытые пункты → `new`/`briefing`/`active` → **`blocked_access`**
* все закрыты → `blocked_access` → `active`
* пока ждём — **одно** напоминание клиенту не чаще `ACCESS_REMINDER_H` (24 ч),
  со **всем списком** недостающего сразу. По пункту на сообщение — это способ
  превратить бота в спам и добиться того, что клиент перестанет читать вообще всё.

`blocked_access` — живой статус, а не терминальный: `chat` в нём работает,
иначе доступы было бы негде просить.

## Секреты

Модуль `autopilot/vault.py`. Правила держатся жёстко, каждое покрыто тестом.

* Значения лежат **только** в `secrets.enc` — Fernet, ключ из `VAULT_KEY`.
  Путь из `VAULT_PATH`, по умолчанию рядом с БД. В `.gitignore` — `secrets.enc`
  и `*.enc`.
* В БД (`AccessItem.secret_ref`, `Task.prompt`, `Project.brief`) хранится
  **ссылка `{{SECRET:NAME}}`**, значения там нет.
* **В промпт значение не подставляется никогда.** `build_prompt()` прогоняет
  текст через `to_env_names()`: `{{SECRET:FTP_PASS}}` → `$FTP_PASS`. Значения
  приходят агенту через `env=` у subprocess, и системный промпт прямо говорит
  брать их из окружения и не печатать.
* `SecretMasker` — фильтр на root-логгере, ставится в `main` до первой записи.
  Вымарывает любое известное значение из логов, включая stdout/stderr Claude
  Code. Вывод агента маскируется и перед записью в `logs/task*.json`.
* В Google-таблицу секреты не попадают ни в каком виде: колонка «Ждём от
  клиента» содержит только **названия** пунктов чеклиста.
* Значения короче 4 символов не маскируются — иначе логи превращаются в решето
  из звёздочек, а короткий секрет всё равно ничего не защищает.

Проверено на живом прогоне: канарейка из хранилища не находится ни в логах, ни
в `autopilot.db`, ни в файлах репозитория.

## Статусы

### Проект: `new → briefing → active → review → done`, плюс `blocked` и `blocked_access`

| переход                     | кто делает                | когда |
|-----------------------------|---------------------------|-------|
| `new → briefing`            | `sheets._pull`            | в строке появился `TG chat` |
| `briefing → active`         | `Scheduler._activate`     | выдан **первый build-слот** (значит галочка стоит и доступы есть) |
| `* → blocked_access`        | `Scheduler._sync_access`  | появился пункт чеклиста не в `verified` |
| `blocked_access → active`   | `Scheduler._sync_access`  | весь чеклист `verified` |
| `active → review`           | `Scheduler._maybe_finish` | не осталось задач вне `done`/`escalated` |
| `review → done`             | **человек**               | работа принята |
| `* → blocked`               | `Scheduler._on_fail`      | задача исчерпала `MAX_ATTEMPTS` |
| `blocked → *`               | **человек**               | разобрался и вернул в работу |

В `_pick` фильтр — `status NOT IN ('done', 'blocked')`: обслуживается всё живое.
В скелете фильтр был `IN ('active','review')`, но никто и никогда не ставил
`active` — `sheets.py` доводил проект только до `briefing`, и задачи не
подхватывались вообще никогда.

### Задача: `pending → ready → running → done | escalated`

* `ready → running` — `_claim()`
* `build` завершился → `status=ready, lane=verify` (та же задача едет на приёмку)
* `verify` PASS → `done` + строка в накопительный отчёт клиенту
* `verify` FAIL → `attempts += 1`, `status=ready`, `lane=build` — назад на
  починку, тем же `cc_session_id`, с дефектами в промпте
* упавшая `build`/`chat` задача остаётся **в своей полосе**
* `attempts >= MAX_ATTEMPTS` → `escalated`, проект → `blocked`

Задачи, зависшие в `running` после убийства процесса, возвращаются в `ready` на
старте (`recover_orphan_tasks()`).

## Google-таблица: кто чей столбец

БД — источник правды, таблица — витрина.

* `HUMAN` — бот только читает: `ID`, `Клиент`, `Проект`, `TG chat`, `Цена`,
  `Дедлайн`, `Приоритет`, `Папка`, **`Готов к работе`**.
* `BOT` — бот перезаписывает батчем: `Статус`, `Прогресс`,
  **`Ждём от клиента`**, `Превью`, `Последнее действие`, `Стоимость $`,
  `Обновлено`.

`Ждём от клиента` — список недостающих доступов, чтобы менеджер видел, почему
проект стоит, и не дёргал владельца.

Единственная запись бота в человеческую колонку — проставленный `ID` у новой
строки в `_pull`, без него строку не связать с проектом. `_push` берёт индексы
только из `BOT` и проверяет ассертом, что они не пересеклись; это же покрыто
тестом `test_sheets_column_ownership`.

Гонки: `loop()` держит `asyncio.Lock`, `_pull` и `_push` идут строго по очереди.
Внутри каждого сетевые вызовы gspread (`asyncio.to_thread`) и работа с БД
разнесены по фазам — сессия БД не держится открытой поверх сетевого вызова.
Пересечений записи со `Scheduler` нет: `_pull` трогает только человеческие поля,
планировщик — только свои.

## Бюджет

`spent_today()` = сумма `Run.cost_usd` за скользящие 24 часа. При достижении
`DAILY_BUDGET_USD` встают `build` и `verify`; `chat` работает всегда — клиент не
должен молчать из-за денег. Флаг пересчитывается каждый тик, полосы
размораживаются сами.

В `Run` пишут оба платных места: `Executor` (`kind="execute"`) и `Verifier`
(`kind="judge"`, стоимость считается по `JUDGE_PRICE_IN/OUT_USD_PER_MTOK` —
SDK её не отдаёт). **Цены прописаны руками**, при смене тарифов бюджет соврёт.

## Время и БД

Все `datetime` внутри процесса — **aware UTC**. SQLite не хранит tzinfo: обычный
`DateTime` молча терял offset и отдавал naive, после чего
`utcnow() - row.updated_at` падало с `TypeError`. Поэтому `UtcDateTime`
(TypeDecorator) в `db.py`. Локальное время появляется в двух местах: колонка
`Обновлено` и проверка тихих часов.

На соединении включены `journal_mode=WAL`, `busy_timeout=10000`,
`foreign_keys=ON`.

Движок создаётся на импорте `autopilot.db` из `cfg.db_url` и позже не
перенаправляется — тесты подменяют `DB_URL` в `conftest.py` **до** импорта.

## Чего в проекте намеренно нет

* **Redis, Celery, Postgres, Docker** — и не будет. Один asyncio-процесс + SQLite.
* `ingest.py` — Telegram Business API → входящие. Следующая фаза.
  **`Communicator.incoming()` уже написан, но вызывать его пока некому.**
* `brief.py` — чат → JSON ТЗ с `confidence` и `open_questions`. Следующая фаза.
* `planner.py` — ТЗ → задачи с machine-checkable acceptance. Следующая фаза.
  **Ни задачи, ни пункты чеклиста доступов сами не появляются** — их кладёт
  `seed_demo.py` или ты руками.
* `checks/` — Playwright-сценарии (375/768/1440, горизонтальный скролл, консоль).
* Реальная отправка в Telegram: `Communicator.send_fn` по умолчанию пишет в лог.
  `TG_BOT_TOKEN` читается конфигом и нигде не используется.
* `Communicator.process` — пустая заглушка: chat-слот выдаётся и сразу закрывается.
* Миграции схемы. `init_db()` делает `create_all`, изменение колонки — руками.
* Ротация секретов и аудит обращений к ним.
* Веб-морда, метрики, авторизация. Таблица и логи — весь интерфейс.

## Что осталось сомнительным

* **Маршрутизация — это список регулярок, а не понимание.** Она не поймёт
  «а можно ещё вот такую штуку сверху?», если там нет ключевых слов, — но
  правило по умолчанию отправит это менеджеру, и в этом смысле промах
  безопасен. Обратная сторона: «сколько страниц уже готово?» тоже уедет
  менеджеру, потому что «сколько» в менеджерской сети. Так и задумано, но
  раздражать будет.
* **Секреты в окружении дочернего процесса** видны этому процессу целиком и,
  на части систем, в `/proc/<pid>/environ`. Это всё равно на порядок лучше
  секрета в промпте, который уедет в облако и осядет в транскрипте, но
  «безопасно» — не то слово.
* **Маскирование работает по точному совпадению.** Если агент выведет пароль
  по частям, в base64 или url-encoded — фильтр его не увидит.
* **Ключ `VAULT_KEY` лежит в `.env` рядом с `secrets.enc`.** Кто получил доступ
  к машине, получил и то и другое. Настоящее разделение — это KMS, которого
  здесь нет и не просили.
* **`verified` ставит человек, автопроверки доступа нет.** Статус означает
  «кто-то сказал, что работает», а не «система проверила».
* **Судья без `ANTHROPIC_API_KEY` валит llm-проверку** (дефект, не молчаливый
  PASS). `JUDGE_OPTIONAL=1` возвращает пропуск с предупреждением. Учти: при
  непройденной проверке задача через `MAX_ATTEMPTS` уедет в эскалацию.
* **Судья, вернувший не-JSON, теперь тоже FAIL** («судья не ответил»). Значит
  флапающий или перегруженный API будет отправлять задачи в эскалацию — следи
  за логами `WARNING судья вернул не-JSON`.
* **`_pull` пишет ID по номеру строки**, снятому до записи. Переставишь строки
  в те же секунды — ID уедет не в ту строку.

## Про архитектуру трёх полос

Менять её не просили и не менял. Замечание одно: `build` и `verify` конкурируют
за одни и те же CPU/API-лимиты, но их квоты независимы (3 и 2), поэтому реальная
одновременная нагрузка — до 5 тяжёлых задач, а не 3. Если начнёт упираться,
правильнее вводить общий лимит на «тяжёлые» полосы, а не резать каждую отдельно.
