# Qorsa Autopilot — карта проекта

Локальный оркестратор фриланс-заказов: Google-таблица → задачи → Claude Code в
headless → приёмка → сообщение клиенту. Один asyncio-процесс + SQLite, больше ничего.

Файл описывает то, что код **делает сейчас**, а не то, что задумывалось.
Если правишь поведение — правь и этот файл.

---

## Запуск

```bash
python -m venv .venv && .venv/Scripts/activate     # Windows; на *nix — source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
cp .env.example .env                                # заполни ANTHROPIC_API_KEY и SHEET_ID
python -m autopilot.main
```

Тесты:

```bash
pytest
```

Посмотреть на планировщик вживую без таблицы, без Telegram и без трат:

```bash
python scripts/seed_demo.py
DRY_RUN=1 python -m autopilot.main
```

`DRY_RUN=1` подменяет `Executor` и `Verifier` заглушками из `autopilot/fakes.py`.
**Без него** демо попытается запустить настоящий `claude`, и если бинаря нет —
каждая задача честно упадёт с `ERROR ... не нашёл claude-бинарь` и через
`MAX_ATTEMPTS` попыток уедет в эскалацию. Это не баг, это отсутствие CLI.

`scripts/seed_demo.py` идемпотентен: сносит только проекты с заголовком `DEMO: …`.

## Три полосы

`cfg.lane_limits` — сколько задач в полосе может идти одновременно.

| полоса   | лимит | эксклюзивная | что делает                              |
|----------|-------|--------------|-----------------------------------------|
| `chat`   | 8     | нет          | `Communicator.process` — ответы клиенту |
| `build`  | 3     | да           | `Executor.run` — Claude Code в headless |
| `verify` | 2     | да           | `Verifier.run` — приёмка                |

**Эксклюзивная** = один проект не может держать два слота этой полосы разом
(`Scheduler.busy_projects`). `chat` не эксклюзивная нарочно: ответы клиенту не
должны ждать за компиляцией и друг за другом.

Занятые слоты считаются в `Scheduler.running[lane]`. Semaphore убран: раньше
код читал приватное `sem._value`, это не публичный API и ломается от версии к версии.

Один тик занимает **не больше, чем свободно на начало тика** (`quota` в `_dispatch`).
Без этого на быстрых задачах цикл вычерпывал всю очередь полосы за один проход,
и «тик» переставал что-либо значить.

## WFQ — кто получает слот

`_pick()` берёт проект с минимальным `served_units / weight(project)`, внутри
проекта — задачу с минимальным `order_idx`.

```
weight = {1: 3.0, 2: 2.0, 3: 1.0}[priority]
         × 4.0 если дедлайн просрочен
         × 2.0 если до дедлайна ≤ 3 дней
```

`served_units` списывается **в момент выдачи слота** (`DISPATCH_UNITS = 1.0`),
а не по завершении. Это важно: пока задача не закончилась, `served_units` не
менялся бы, и проект с 40 задачами забирал бы все свободные слоты одного тика.
По завершении добивается только превышение над авансом:
`max(длительность_в_минутах − 1.0, 0)`. То есть короткая задача стоит ровно 1,
длинная — столько минут, сколько шла.

`served_units` монотонно растёт и никогда не обнуляется. Для порядка обслуживания
это неважно (сравниваются отношения), но абсолютные значения — счётчик за всё
время жизни проекта, не «за сегодня».

### Захват задачи

`_pick()` возвращает **кандидата**, право на работу выдаёт `_claim()` — один
условный `UPDATE tasks SET status='running' WHERE id=? AND status='ready'`.
Так сделано не для красоты: `_pick` фильтрует свежий `inflight` по снимку из БД,
снятому чуть раньше, и в окне между запросом и фильтрацией задача успевала
доработать, выйти из `inflight` и быть выданной второй раз. Ловилось на тесте
приоритетов: 336 запусков на 240 задач.

## Бюджет

`spent_today()` = сумма `Run.cost_usd` за скользящие 24 часа (не календарные сутки).
Как только она ≥ `DAILY_BUDGET_USD`, `tick()` перестаёт диспатчить `build` и
`verify`; `chat` работает всегда — клиент не должен молчать из-за денег.
Флаг пересчитывается каждый тик, так что при выпадении старых `Run` из окна
полосы размораживаются сами.

В `Run` пишут оба платных места: `Executor` (`kind="execute"`, стоимость от
Claude Code) и `Verifier` (`kind="judge"`, стоимость считается по
`JUDGE_PRICE_IN/OUT_USD_PER_MTOK` — SDK её не отдаёт). **Цены прописаны руками,
при смене тарифов их надо править**, иначе бюджет будет врать.

## Статусы

### Проект: `new → briefing → active → review → done | blocked`

| переход              | кто делает                        | когда |
|----------------------|-----------------------------------|-------|
| `new → briefing`     | `sheets._pull`                    | в строке таблицы появился `TG chat` |
| `briefing → active`  | `Scheduler._activate`             | проекту выдан **первый build-слот** |
| `active → review`    | `Scheduler._maybe_finish`         | не осталось задач вне `done`/`escalated` |
| `review → done`      | **человек**                       | работа принята |
| `* → blocked`        | `Scheduler._on_fail`              | задача исчерпала `MAX_ATTEMPTS` |
| `blocked → *`        | **человек**                       | разобрался и вернул в работу |

Это ответ на вопрос «где правильный переход статусов». В скелете `_pick`
фильтровал `Project.status.in_(("active", "review"))`, но никто и никогда не
ставил `active` — `sheets.py` доводил проект только до `briefing`. Задачи не
подхватывались вообще никогда.

Чинить это сужением фильтра было бы неправильно: сам факт «у проекта есть
готовая задача» и означает, что брифинг кончился. Поэтому:

* фильтр в `_pick` — `status NOT IN ('done', 'blocked')`, то есть обслуживается
  всё живое;
* `active` проставляется в момент выдачи build-слота, а не раньше — до появления
  задач проект действительно ещё брифуется;
* полосу `chat` статус `briefing` не блокирует: уточнять ТЗ надо именно там.

`review → done` и `blocked → работа` кодом не делаются нигде и делаться не должны:
это решения человека.

### Задача: `pending → ready → running → done | escalated`

* `ready → running` — `_claim()`
* `build` завершился → `status=ready, lane=verify` (та же задача едет на приёмку)
* `verify` дал PASS → `done` + сообщение клиенту
* `verify` дал FAIL → `attempts += 1`, `status=ready`, **`lane=build`** — назад на
  починку, тем же `cc_session_id`, с дефектами в промпте
* упавшая `build`/`chat` задача остаётся **в своей полосе**. В скелете любой
  провал переставлял `lane="build"`, и упавшая chat-задача превращалась в
  сборочную — это меняет её смысл.
* `attempts >= MAX_ATTEMPTS` → `escalated`, проект → `blocked`

Задачи, зависшие в `running` после убийства процесса, возвращаются в `ready`
на старте (`recover_orphan_tasks()` в `main`).

## Google-таблица: кто чей столбец

БД — источник правды, таблица — витрина.

* `HUMAN` (`ID`, `Клиент`, `Проект`, `TG chat`, `Цена`, `Дедлайн`, `Приоритет`,
  `Папка`) — бот только читает.
* `BOT` (`Статус`, `Прогресс`, `Превью`, `Последнее действие`, `Стоимость $`,
  `Обновлено`) — бот перезаписывает батчем.

Единственная запись бота в твою колонку — проставленный `ID` у новой строки в
`_pull`, без него строку не связать с проектом. `_push` жёстко берёт индексы
только из `BOT` и проверяет ассертом, что они не пересеклись с человеческими;
это же покрыто тестом `test_sheets_column_ownership`.

Порядок и гонки: `loop()` держит `asyncio.Lock`, `_pull` и `_push` идут строго
по очереди и никогда параллельно. Внутри каждого сетевые вызовы gspread
(`asyncio.to_thread`) и работа с БД разнесены по фазам — сессия БД не держится
открытой поверх сетевого вызова. Клиент gspread кэшируется и пересоздаётся
только после ошибки цикла.

Пересечений записи со `Scheduler` нет: `_pull` трогает только человеческие поля
(плюс `new → briefing`), планировщик — только `status`/`served_units`/`cost_usd`/
`last_action`. SQLAlchemy пишет в `UPDATE` лишь изменённые колонки, так что
затирания чужих полей не будет.

## Гейты сообщений

`classify(text)`:

* **red** — есть слово из `RED_WORDS` (цена, скидк, оплат, договор, срок, гарант…)
* **yellow** — есть `?`
* **green** — остальное

Красное сохраняется как `draft` с `send_after=None` и **не уходит никогда**,
пока ты сам не отправишь. Жёлтое/зелёное становится `scheduled` с человеческой
задержкой (10 мин для жёлтого, 40–900 с для зелёного).

Гейт всегда берётся **самый строгий** из вычисленного и запрошенного
(`strictest`). В скелете `on_task_done` передавал `gate="green"` напрямую, и
любой заголовок задачи со словом «скидка» уезжал клиенту без подтверждения.

`pump_once()` шлёт только `status="scheduled"` и `gate != "red"` с наступившим
`send_after`. Тихие часы (`QUIET_START`/`QUIET_END`) считаются по **локальному**
времени машины; равные границы выключают тишину. Сообщение проекта без
`tg_chat_id` помечается `cancelled`, а не висит вечно.

## Время и БД

Все `datetime` внутри процесса — **aware UTC**. SQLite не хранит tzinfo: обычный
`DateTime` молча терял offset и отдавал naive, после чего `utcnow() - row.updated_at`
падало с `TypeError`. Поэтому в `db.py` есть `UtcDateTime` (TypeDecorator):
пишет naive-UTC, читает aware-UTC, naive на входе трактует как UTC.
Локальное время появляется ровно в двух местах: колонка `Обновлено` в таблице и
проверка тихих часов.

`deadline` — `date`, сравнивается с `dt.date.today()` (локальная дата: дедлайн
живёт в календаре человека, а не в UTC).

На соединении включены `journal_mode=WAL`, `busy_timeout=10000`,
`foreign_keys=ON`. WAL и таймаут — потому что планировщик и синк таблицы пишут в
одну базу из разных корутин. FK включены осознанно: `Run` без существующей
задачи теперь не вставится.

Движок создаётся на импорте `autopilot.db` из `cfg.db_url`, перенаправить его
позже нельзя — тесты подменяют `DB_URL` в `tests/conftest.py` **до** импорта.

## Чего в проекте намеренно нет

* **Redis, Celery, Postgres, Docker** — и не будет. Один asyncio-процесс + SQLite.
* `ingest.py` — Telegram Business API → таблица `messages`. Следующая фаза.
* `brief.py` — чат → JSON ТЗ с `confidence` и `open_questions`. Следующая фаза.
* `planner.py` — ТЗ → задачи с machine-checkable acceptance. Следующая фаза.
  **Пока задачи в БД не появляются сами** — их кладёт либо `seed_demo.py`, либо ты.
* `checks/` — Playwright-сценарии (375/768/1440, горизонтальный скролл, консоль).
* Реальная отправка в Telegram: `Communicator.send_fn` по умолчанию пишет в лог.
  `TG_BOT_TOKEN` читается конфигом и нигде не используется.
* `Communicator.process` — пустая заглушка: chat-слот выдаётся и сразу закрывается.
* Миграции схемы. `init_db()` делает `create_all`, изменение колонки — руками.
* Веб-морда, метрики, авторизация. Таблица и логи — весь интерфейс.

## Что осталось сомнительным

* **`RED_WORDS` дырявый.** Список ловит «стоимость», но не «стоить»: фраза
  «сколько это будет стоить?» классифицируется как **yellow** и уйдёт клиенту
  сама через 10 минут. Не трогал специально — словарь гейта это твой голос
  перед клиентом, дополнять его тебе.
* **Судья без ключа.** Без `ANTHROPIC_API_KEY` llm-проверка считается
  **непройденной** (дефект), а не молча пропущенной: молчаливый PASS прямо
  противоречит смыслу модуля. `JUDGE_OPTIONAL=1` возвращает старое поведение —
  пропуск с предупреждением. Учти, что при непройденной проверке задача через
  `MAX_ATTEMPTS` уедет в эскалацию.
* **Судья, вернувший не-JSON, засчитывается как PASS.** Оставлено как было,
  но теперь это видно в логах (`WARNING судья вернул не-JSON`).
* **Цены судьи захардкожены** (`JUDGE_PRICE_*`), при смене тарифов бюджет врёт.
* **`served_units` не стареет.** Проект, простоявший месяц, стартует с огромным
  счётчиком и в WFQ проигрывает новичкам. Пока проектов немного — незаметно.
* **`_pull` пишет ID по номеру строки**, снятому до записи. Если ты переставишь
  строки местами между чтением и записью (секунды), ID уедет не в ту строку.
* **`on_task_done` шлёт сообщение на каждую закрытую задачу.** На демо это 80
  сообщений за две минуты. Для живых клиентов сюда явно нужна агрегация.

## Про архитектуру трёх полос

Менять её не просили и я не менял. Замечание одно: `build` и `verify` конкурируют
за одни и те же CPU/API-лимиты, но их квоты независимы (3 и 2), поэтому реальная
одновременная нагрузка — до 5 тяжёлых задач, а не 3. Если начнёт упираться,
правильнее вводить общий лимит на «тяжёлые» полосы, а не резать каждую отдельно.
