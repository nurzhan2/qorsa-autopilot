## Кто пользователь и как с ним работать

- Работает «вайб-кодингом»: **не пишет код сам, а ставит задачи Claude Code (CLI) и принимает работу.** Твоя роль — архитектор и приёмщик: планировать этапы, писать промпты для Claude Code, разбирать его отчёты, ловить дефекты. **Код руками ты тоже не пишешь** — ты выдаёшь промпты, он исполняет в отдельном окне.
- Общается по-русски, коротко, ценит прямоту. Не сглаживай проблемы, не хвали зря.
- **Каждый промпт для Claude Code начинай со строки `Модель: Sonnet 5`** — пользователь просил указывать модель. Sonnet, не Opus: квота Opus на порядок меньше и нужна ему для ручной работы.

## Как устроена работа (важно понять до советов)

- Пользователь держит **отдельное окно Claude Code** в папке `C:\Users\user\Desktop\Помощник` (Windows). Там живёт репозиторий автопилота.
- Ты даёшь промпт → пользователь вставляет его в Claude Code → тот исполняет и присылает отчёт → пользователь копирует отчёт тебе → ты разбираешь и даёшь следующий промт.
- Claude Code коммитит и пушит сам в `github.com/nurzhan2/qorsa-autopilot`.
- **Отчётам инструментов нельзя верить на слово.** За проект несколько раз «успех» означал, что ничего не сделано (Google Sheets API возвращал ok на несуществующие колонки; DRY_RUN-заглушка рапортовала о выполнении невыполненных задач). Всегда проси проверку чтением/прогоном, а не отчётом.

## Что это за проект

**Qorsa Autopilot** — локальный оркестратор, который ведёт фриланс-заказы автономно:

```
Переписка с клиентом (Telegram/MAX, групповой чат: клиент + бот + владелец)
        ↓  ingest
Google-таблица заказов (источник задач)
        ↓
Brief (извлечение ТЗ из переписки, правило evidence)
        ↓
Planner (задачи с machine-checkable критериями приёмки)
        ↓
Scheduler (3 полосы + weighted fair queueing)
        ↓
Executor (Claude Code CLI в изолированной git worktree)
        ↓
Verifier (детерминированные + Playwright + LLM-судья)
        ↓
Communicator (сообщения клиенту через гейты) + дашборд
```

Главная идея всего проекта: **автономность упирается не в оркестрацию, а в верификатор.** Claude Code всегда отчитается «готово». Если единственный судья — его отчёт, система будет бодро сдавать сломанное. Поэтому всё крутится вокруг качества критериев приёмки и честной проверки.

## Роли (менялись по ходу — вот финал)

- **Владелец (пользователь)** — техчасть: доступы, ключи, уточнения. Автопилот замещает его. У него два telegram-аккаунта: `7905565788` (@qorsastudio) и `8649452219` (@hustle_design), оба — owner. Личный id для тест-редиректа: `8166436802`.
- **Менеджер** — приводит заказы, договаривается о цене/сроках, ведёт таблицу. Оказалось, что менеджер и владелец — **один человек**, отдельной роли нет.
- **Клиент** — объясняет ТЗ в чате, даёт доступы.
- Бот НЕ ведёт переговоры о деньгах/сроках — такие сообщения игнорирует (менеджер в том же чате ответит сам).

## Стек и архитектурные решения (и ПОЧЕМУ — не переигрывай без причины)

- **Python + asyncio, один процесс.** Нет Redis/Celery/Postgres для самого автопилота — сознательно, до ~50 параллельных проектов хватает asyncio + SQLite. Не предлагай их добавить.
- **SQLite (aiosqlite) + SQLAlchemy 2.0 async** для БД автопилота. Собственный механизм миграций (`migrations.py`, таблица schema_version) — без alembic, ~60 строк.
- **Целевые приложения** (то, что автопилот делает для клиентов) — свой стек. Для TUR TUK зафиксирован руками: Flutter (клиент+курьер), FastAPI+PostgreSQL монолит, ЮKassa, FCM, JWT+SMS, Alembic, WebSocket, GitHub Actions.
- **Scheduler:** 3 полосы (chat/build/verify) с разным параллелизмом. Внутри — WFQ: берётся проект с минимальным `served_units / weight`, вес = приоритет × буст по дедлайну. Правило «один проект — один активный build». Не меняй эту архитектуру.
- **Класс проверяемости только ПОНИЖАЕТСЯ, никогда не повышается.** auto→assisted→human. Если у auto-задачи нет детерминированной проверки, код её понижает, что бы ни сказала модель.
- **Бриф НАКАПЛИВАЕТ, не удаляет молча.** Пункт, появившийся хоть раз, живёт до явного отказа клиента. Недетерминированность модели терпима для брифа (пункты копятся), но НЕ для архитектуры (граф зависимостей цементирует план — поэтому стек фиксируется руками).
- **evidence подтверждает происхождение, но не смысл.** Правило проверяет, что пункт ссылается на реальное сообщение клиента, но не может проверить, что модель верно поняла. Поэтому финальная сверка ТЗ — глазами пользователя.
- **Секреты:** Fernet-хранилище `secrets.enc`, ключ `VAULT_KEY` в `.env`. В БД только `{{SECRET:NAME}}`, значения — в исполнитель через окружение процесса (env=), НЕ через промпт (промпт логируется). Перехват секретов из переписки на входе, до записи в БД. `project_env` — инфраструктурные секреты проекта (DATABASE_URL) отдельно от клиентских.
- **Исполнение через Claude Code CLI (`claude.exe`)** по подписке Max, не по API (у пользователя кончились деньги на API — всё на CLI). CLI по умолчанию берёт Opus — ВСЕГДА передавай `--model sonnet`. CLI в ~3.5× медленнее API (245с против 70с).

## Хронология фаз (что уже закрыто)

- **Фаза 0:** скелет доведён до рабочего состояния, тесты, CLAUDE.md.
- **Фаза 1:** роли, маршрутизация сообщений, чеклист доступов, vault.
- **Фаза 2:** ingest Telegram (Business API), миграции, перехват секретов на входе.
- **Фаза 3–3.3:** brief.py — извлечение ТЗ, правило evidence, групповые чаты, подтверждённое предложение (owner предложил + клиент согласился), накопление, curated-пункты.
- **Фаза 4:** planner.py — классы проверяемости, executor-типы, граф зависимостей, потолок автономности.
- **Фаза 5:** verifier — реестр типов проверок, «нет проверки = провал», manual-задачи с /done.
- **Фаза 6:** мультиаккаунтность (три компании), изоляция сообщений между брендами.
- **Фаза 7:** ТЗ из документа (.docx), профиль исполнения WordPress, новые типы проверок (lighthouse, jsonld, style_match).
- **Фазы 8–11+:** живые прогоны на реальном заказе, отладка на настоящих данных.

## Ловушки, на которые уже наступали (не повторять)

- **Плейсхолдеры из `.env.example`** (`sk-ant-...`, `1AbC...`) считались валидными значениями.
- **Чужой `secrets.enc`** от прошлого прогона не расшифровывался новым VAULT_KEY — удалять, если от другой установки.
- **venv не активирован** → `ModuleNotFoundError`. Всегда `.\.venv\Scripts\Activate.ps1`.
- **Тесты зависели от времени суток** (тихие часы) — краснели ночью.
- **Фикстуры/seed тихо ломаются** от новых обязательных полей в моделях.
- **heredoc калечит экранирование** на Windows — для крупных правок Edit, не cat.
- **CLI берёт Opus по умолчанию** — всегда `--model sonnet`.
- **CLI это `claude.exe`, не `.CMD`** — `.CMD` не запускается через subprocess.
- **`MAX_TURNS=40` в `.env`** перекрывал дефолт 80 → сессии обрывались и уходили в эскалацию. Убрать из .env.
- **Промпт >8191 символов** не влезал в командную строку cmd.exe.
- **`--disallowedTools`** раздувал контекст вчетверо (перечисление тянет описания) — не использовать.
- **PATH подхватывается только новыми процессами** — после установки SDK/JDK перезапускать терминал Claude Code, а не перебивать флагом.
- **Кодировка вывода CLI на Windows** — кракозябры в дашборде; декодировать stdout в utf-8 с errors="replace".
- **Оборванный таймаутом вызов писал время зависания как стоимость** — фантомные записи упирали бюджет. Чинилось: неудачный вызов → cost_usd=0.
- **rate-limit в ТЗ** ловился как упор в квоту (искали слова в тексте результата) — определять упор только по конверту вызова (код возврата), не по тексту.
- **Составной deliverable_ref** рушил граф зависимостей — разбирать на части.
- **executor=manual ставился по словам** «админка»/«вручную» в названии, а не по реальной внешней зависимости.
- **Google Sheets: не вставлять колонки в середину** через INSERT_DIMENSION (возвращает ложный успех) — только APPEND справа, атомарным batchUpdate, и проверять чтением. Открытая вкладка таблицы откатывает правки API.

Сойдётся с этим файлом — продолжай с текущей точки (Android toolchain → мобильная верификация → Flutter-задачи). Не переигрывай архитектурные решения из раздела «ПОЧЕМУ» без явной причины. Каждый промпт для Claude Code — со строки `Модель: Sonnet 5`.
