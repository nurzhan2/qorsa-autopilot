## Чего делать НЕЛЬЗЯ

* Не трогать планировщик полос и WFQ. Это осознанный потолок, см. HANDOFF §5.
* Не заводить Redis, Celery, Postgres или Docker под сам автопилот.
  Один asyncio-процесс и SQLite.
* **Не ослаблять критерии приёмки ради прохождения.** Критерий — это и есть
  приёмка. Всюду ниже, где речь о правке критерия, действует один закон:
  новый критерий обязан ПАДАТЬ на текущем состоянии кода до правки. Если
  он проходит сразу — он пустышка, отвергнуть.
* Не поднимать класс проверяемости. Он только понижается.
* Не делать правки с кавычками и переносами через heredoc с python внутри —
  `\n` там превращается в настоящий перенос посреди f-строки. Только Edit/Write.
* Молчаливый пропуск проверки — худший режим системы. Неизвестный случай —
  это провал, а не основание пропустить.

# Фаза 2. Сторож времени: прогон не может висеть четыре часа

**Что случилось.** `CLI_TIMEOUT_SEC` держится на `asyncio.wait_for`, а тот
считает по таймеру цикла событий. Пока Windows спит, цикл заморожен вместе
с дочерним процессом. Живой случай из HANDOFF: `Run` 67 — 276 минут вместо
30. В базе сейчас 25 оборванных execute со средней 43 минуты и 7 планов
со средней 77.

Сделай три вещи, все в `autopilot/executor.py` и `autopilot/llm.py`:

1. **Дедлайн по настенным часам.** Помимо `wait_for`, держи абсолютный
   дедлайн по `time.time()` и проверяй его на каждом тике. Проснулись —
   увидели, что срок вышел, убили. Не заменяй `monotonic` там, где он
   меряет длительность: он честен. Речь только о решении «пора убивать».

2. **Пульс по выводу ребёнка.** Если дочерний процесс молчит дольше
   `CLI_SILENCE_SEC` (новая настройка, дефолт 300), это мёртвый прогон —
   убивать, не дожидаясь общего таймаута. Молчание CLI и работа CLI
   различимы: он пишет в stdout по ходу.

3. **Запрет сна на время прогона.** Через `ctypes`:
   `kernel32.SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)`
   на старте прогона, `ES_CONTINUOUS` в одиночку — на выходе, обязательно
   в `finally`. Константы: `ES_CONTINUOUS=0x80000000`,
   `ES_SYSTEM_REQUIRED=0x00000001`. На не-Windows — no-op, не падать.

4. **Уборка призраков при старте.** Строки `runs` с пустым `finished_at`
   старше суток — это вызовы, которые не вернулись. Закрывай их при
   запуске процесса: `ok=0`, `cost_usd=0` (оценка по времени была багом,
   см. HANDOFF §6 — не возвращай её), `finished_at` = момент уборки,
   и пометка в логе. Сейчас таких четыре: id 157, 174, 177, 185.

Настройки — в `.env.example` тоже, и через `vault._usable()`, чтобы
плейсхолдер не сошёл за значение.

Тесты: молчащий процесс убивается по `CLI_SILENCE_SEC`; проснувшийся
после «сна» процесс убивается по настенному дедлайну (подделай часы,
не спи по-настоящему); уборка призраков не трогает живые строки.

# Фаза 6. Реабилитация: причина исчезла — задача возвращается сама

Это ядро задания. Фаза 1 расшивает 536 и 547 руками; здесь ты делаешь так,
чтобы руки больше не понадобились.

**Идея.** Задача, ушедшая в `needs_human` или `escalated`, получает
**отпечаток причины** — машинно-проверяемое условие, при котором она встала.
Планировщик периодически перепроверяет отпечатки терминальных задач. Условие
больше не выполняется — задача возвращается в `ready` сама, `attempts`
обнуляются, в лог и владельцу уходит строка «встала из-за X, X больше нет,
вернул в работу».

**Виды отпечатков** (заводи как явный набор, неизвестный вид — провал,
а не «наверное, сойдёт»):

```
unrunnable:<команда>   критерий звал команду, которой не было
                       перепроверка: команда доступна тем же путём,
                       которым её будет звать приёмка (включая git-bash PATH)
missing_tool:<tool>    toolchain.installed(tool) стало True
env:<вид>              классификатор из фазы 5 больше не срабатывает
                       на повторном прогоне критерия
backend:<имя>          preflight из фазы 4 стал проходить
limit                  окно упора в квоту закрылось
code:<sha>             задача встала до коммита X; HEAD с тех пор изменился
                       в файлах, которых она касалась
```

Требования:

* Отпечаток ставится ТАМ, ГДЕ ПРИНИМАЕТСЯ решение остановиться —
  в `scheduler._diagnose`, в ветке эскалации, в обработчике
  `unrunnable_reason`. Не задним числом и не догадкой по тексту `last_error`.
* Хранение: новая колонка у `Task` (`stall_fingerprint`, TEXT, nullable) +
  миграция. Следующий номер — **15**, в базе сейчас 14. Булевым колонкам
  давай `server_default`; `INSERT OR IGNORE` в миграции глотает не только
  дубли (HANDOFF §6) — после переноса явно сверяй количества.
* Добавил обязательное поле — проверь `tests/conftest.py` и
  `scripts/seed_demo.py`. Это ломалось уже четырежды.
* Перепроверка — дешёвая и без модели. Никаких LLM-вызовов в этом цикле.
* Возврат в работу — **не тихий**. Строка в лог и уведомление владельцу.
* Задача без отпечатка не реабилитируется никогда. Отпечаток есть только
  у того, что мы умеем проверить; всё остальное честно ждёт человека.
* Реабилитация не отменяет `MAX_ATTEMPTS` навсегда: считай циклы
  реабилитации отдельно, потолок (`MAX_REHABS`, дефолт 3) — чтобы задача
  не начала ходить по кругу «встала — вернули — встала».

Тест: задача с `unrunnable:tail` при отсутствующем `tail` остаётся стоять;
при появившемся — возвращается ровно один раз и с обнулёнными попытками.

# Фаза 7. Диагност получает право чинить

**Что случилось.** `crew.Diagnostician` выдаёт вердикт, а
`crew.instruction_block()` применяет его **только при `work_wrong`**.
Остальные три вердикта в `scheduler.py:914` ведут прямо в `NEEDS_HUMAN`.
Между тем живые диагнозы были машинно-исполнимыми: по 536 модель написала
«прогони `flutter build apk --debug` БЕЗ обрезки, приложи полный вывод»,
по 547 — «проверочная команда падает на Windows из-за отсутствия tail».
Ни то, ни другое не работа для человека.

Заведи исполнителя под каждый вердикт. Каждый — отдельная, тестируемая
функция; ни один не имеет права объявить задачу выполненной.

**`criterion_wrong` — предложить замену критерия, но доказать её.**
Порядок жёсткий, и он же снимает страх подделки приёмки:

1. модель предлагает новый критерий;
2. новый критерий прогоняется **на текущем состоянии кода, ДО правки**;
3. если он проходит — это пустышка, отвергнуть и уйти в `needs_human`.
   Критерий обязан падать на состоянии «эта задача не выполнена»;
4. `checks.suspicious()` на нём тоже обязан молчать;
5. только тогда критерий заменяется, старый сохраняется рядом в истории,
   владельцу уходит уведомление с обоими текстами.

**`missing_tool` — починить окружение, а не критерий.**
`toolchain.installed()` → попытка починки PATH (`unix_tools_dir()` уже
умеет это для юникс-утилит) → повтор. Установку пакетов НЕ делай
самовольно: не хватает того, чего нет на машине — это отпечаток
`missing_tool:<tool>` и уведомление, дальше фаза 6 подхватит, когда
владелец поставит.

**`unclear` — не эскалация, а пересъём доказательств.**
Диагност сказал «причину назвать не удалось» ровно потому, что критерий
скрыл вывод за `tail -1 | grep`. Значит: перезапустить критерий без
обрезки, собрать полный вывод (последние 200 строк), приложить и отдать
диагносту ещё раз — **один** раз. Второй `unclear` подряд — человек.

**`work_wrong`** — как сейчас, `instruction_block()` в промпт агенту.

Ограничения: каждый исполнитель ставит отпечаток из фазы 6; ни один
не запускается больше раза за попытку; `LimitReached` пробрасывается
наверх, а не глотается.

# Порядок и режим работы

Фазы делай по одной, в этом порядке: **1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 9**.
Фаза 6 опирается на 4 и 5, фаза 7 — на 6. Не забегай вперёд.

После каждой фазы:

1. `.venv\Scripts\python.exe -m pytest -q` — зелёных не меньше, чем
   в замере фазы 0;
2. отдельный коммит с осмысленным сообщением в стиле репозитория —
   одна строка о том, что теперь работает иначе, а не «фикс»;
3. **отчёт в чат по одному формату: что сделал, что нашёл сверх списка,
   что осталось сомнительным.** Не сглаживай. Плохие новости про качество
   важнее зелёной галочки.

Если тест начал плавать — это сообщение о гонке в коде, а не о плохом
тесте. Разбирайся с гонкой. Один такой уже стоил двух суток.

Если фаза требует живого прогона — он долгий (бриф ~4 минуты, план ~13,
сборка до получаса). Запускай в фоне и жди, не обрывай: оборванный
`brief_eval` однажды пережил SIGTERM, продолжил работать и жёг квоту.
