### Что НЕ доделано — по важности

1. **План на CLI ни разу не собрался.** Две попытки: первая упёрлась
   в `CLI_TIMEOUT_SEC=600` (поднят до 1800, коммит `df1446c`), вторую
   пришлось снять руками — обнаружились два одновременных процесса
   `plan_eval` на одном проекте, оба пишут задачи через `_persist`.
   Цифры плана проекта 8 остались от API-прогона. **Первое, что стоит
   сделать в новом окне: `plan_eval --project 8` и посмотреть, укладывается
   ли он в 1800 секунд.**

2. **Судья оценивает НЕ ТОТ ВОПРОС.** Проверено на живом CLI: задача
   «проверка подписи вебхука + переход заказа в paid», в дифе есть и то
   и другое буквально — судья вернул FAIL с девятью дефектами (нет
   middleware для raw body, нет идемпотентности, нет try/catch, в дифе
   не видно импортов). Замечания разумные, но **ни одно не про заявленный
   критерий**: он съехал с приёмки на общее ревью кода. На живом проекте
   такая задача провалится `MAX_ATTEMPTS` раз и уедет в эскалацию, хотя
   критерий выполнен. Формат при этом в порядке — чистый JSON, терпимый
   парсер не понадобился. Чинить надо `JUDGE_PROMPT`: он говорит «исходи
   из того, что дефекты есть», и модель исходит, забывая, что проверяет
   конкретный критерий, а не проект целиком.

3. **Мультиаккаунтность не проверена живьём.** Два бот-токена в vault есть
   (`QORSA_BOT_TOKEN`, `HUSTLE_BOT_TOKEN`, по 46 символов), но ingest
   с двумя подключениями одновременно ни разу не запускался. Изоляция
   отправки покрыта только тестами.

4. **MAX не проверен ничем.** Токена нет и взять негде: MAX пускает на
   платформу только верифицированные юрлица РФ — внешняя блокировка на
   стороне владельца. Компания `maxru` в `accounts.toml` стоит
   `active=false`. Открытый вопрос, на который нет ответа в документации:
   нужны ли боту права администратора в группе MAX, чтобы видеть все
   сообщения (аналога `/setprivacy` в описании нет).

5. **Первая запись в рабочую таблицу не делалась.** Синк гонялся только
   на чтение.

## 4. Что показали ЖИВЫЕ ДАННЫЕ, чего не показывали тесты

Самый ценный раздел. Каждый пункт стоил отдельного разбирательства, и ни
один не был виден на синтетике.

**Обрезка контекста считала СООБЩЕНИЯ, а не объём.** Последние 80 реплик
целиком, остальные обрубком в 120 символов. Заполненный клиентом бриф на
3851 символ оказался 53-м с конца и дошёл до модели как 120 знаков. Вся
переписка весила 15 тысяч символов и влезала целиком. Цена измерена:
**4 пункта ТЗ вместо 33**. Теперь бюджет в токенах, а длина сообщения
считается признаком содержательности: под нож идут короткие и старые.

**`text_truncated` в `unreadable[]` был сигналом модели, что её обделили
данными, — и мы его игнорировали.** Модель честно перечисляла обрезанные
сообщения, а код принимал бриф как есть. Теперь это жёсткая ошибка прогона:
CRITICAL, уведомление владельцу, бриф не принимается. Отличать от
нечитаемого вложения обязательно: «не вижу, что на фото» — свойство данных,
«текст обрезан» — наш промах.

**`.CMD` не запускается через `create_subprocess_exec`.** npm на Windows
ставит `claude.CMD`, CreateProcess обёртки исполнять не умеет — падало
с «не удаётся найти указанный файл», хотя файл на месте. Рядом лежит
настоящий `claude.exe`, `resolve_cli()` берёт его.

**Промпт не влезал в командную строку.** Через `cmd.exe` предел 8191
символ, промпт брифа — пятнадцать тысяч. Возвращалась обрубленная
абракадабра с покалеченной кириллицей вместо внятной ошибки. Промпт теперь
уходит в stdin.

**`--disallowedTools` раздувает контекст вчетверо.** Перечисление
инструментов по именам подтягивает их описания: 26k токенов кэша против
6.7k без него. Запрещать поимённо то, что и так не разрешено пустым
allowlist, — значит платить за список запретов. Замерено по отдельности,
вместе с заменой системного промпта и отключением динамических секций
(46.6k → 6.8k).

**CLI по умолчанию берёт Opus.** Один вызов из трёх слов стоил владельцу
$0.126. `--model sonnet` передаётся ВСЕГДА и явно; `Reply.models` показывает,
какая модель ответила НА САМОМ ДЕЛЕ. Проверено: резолвится в
`claude-sonnet-5`. Вторая модель в ответе — `haiku-4-5`, это внутренний
вызов самого Claude Code, не наш.

**CLI медленнее API в 3.5 раза.** Замер на девяти вызовах брифа против
девяти API: **245 секунд против 70**. API стабилен (66–73), CLI гуляет
(188–316). Сбор брифа в три прогона: 3.5 минуты на API против 12 на CLI.
Отсюда и `BRIEF_SAMPLES=1` по умолчанию.

**Судья съезжает с критерия на общее ревью** — см. раздел 1, пункт 2.

**Откушенный последний символ у пароля в vault.** Ловилось раньше, поэтому
теперь целостность проверяется программно: значение подставляется обратно
в текст сообщения и сверяется с исходником байт в байт. На проекте 8
проверено — совпало.

**Составной `deliverable_ref` рушил граф зависимостей.** Модель склеивает
несколько пунктов в одну ссылку («Клиентское приложение (must); Админ-панель
(must)»), целиком такая строка не совпадала ни с чем. Пять задач выброшены,
включая инициализацию репозитория и E2E-тестирование, следом код снял
зависимости на несуществующие задачи — граф разъехался у шести штук.
`split_ref()` разбирает составную ссылку.

**Дедлайн и бюджет вырезались постфильтром.** Клиент прямо писал «первая
версия к началу сентября, бюджет 150 тысяч», а запрет «не лезь в деньги
и сроки» выбрасывал это вместе с разговорами о цене. Следствие: планировщик,
не зная про две недели и 150 тысяч, предложил **микросервисы за API Gateway
с PostgreSQL и Redis** на приложение для одного города с полусотней заказов
в день. Теперь это справочные поля `deadline`/`budget`, и они уходят
планировщику блоком «РАМКИ ПРОЕКТА».

**Заодно тот же фильтр убил бы деньги ВНУТРИ продукта:** промокоды,
минимальную сумму заказа 3000 ₽, расчёт стоимости доставки. `is_commercial()`
теперь различает по контексту, а `open_questions` освобождены от фильтра
совсем — вопрос ничего не обещает клиенту.

**Модель не знает сегодняшнего числа.** Сначала прочитала «начало сентября»
как прошлогоднюю дату (дала бы проекту вечный четырёхкратный вес в WFQ),
потом посчитала до сентября 2026 «14 месяцев», хотя оставалось две недели.
Дата теперь идёт в оба промпта явно, остаток считает код.

## 5. Решения и их основания

**Класс проверяемости только ПОНИЖАЕТСЯ.** Модель честно сказала `human`
про «вёрстку по макету Figma», но прицепила `http 200` — и код поднял класс
до `auto`. План вышел «100% авто», включая финальное тестирование заказа.
Признание модели в непроверяемости весомее наличия формальной проверки.
Та же логика у `executor`.

**Бриф НАКАПЛИВАЕТ и не удаляет.** Модель недетерминирована: два прогона
по одному чату дают разный состав. Потерянный отказ вернётся сам, а
потерянное требование просто не попадёт в план, и этого никто не заметит.
Единственный автоматический путь удаления — явный отказ клиента.
Побочный эффект виден на проекте 8: бриф там смешанный (раздел 3).

**Оценка модели ≠ зелёный тест.** `screenshot` и `llm` дают вердикт, который
мы сами называем подсказкой. Задача, прошедшая только ими (или только
критериями, которые `suspicious()` считает пустышками), не закрывается сама
— уходит на `/confirm`. Иначе «готово» означало бы, что модель одобрила
скриншот.

**Нет Redis/Celery/Postgres/Docker.** Один asyncio-процесс и SQLite — это
осознанный потолок. Нагрузка — до полусотни проектов одного человека; всё
сложнее добавляет операционную работу владельцу, который и так один.
Планировщик полос и WFQ написаны под это, менять их запрещено.

**Исполнение на ПОДПИСКЕ, а не на API — потому что денег на API нет.**
`LLM_BACKEND=cli` по умолчанию. API остался рабочим, возврат — одна
переменная. Отсюда же раздельный учёт: `spent_today()` считает только
`backend="api"`, иначе суточный бюджет вставал бы на пустом месте, когда
всё идёт по подписке и не тратится ни рубля.

**Упор в квоту — НЕ провал работы.** Попытка не засчитывается, бриф не
обнуляется, встаёт вся работа сразу, владельцу сообщаем раз за инцидент.
Четыре упора подряд иначе увели бы живую задачу в эскалацию.

**Evidence подтверждает ПРОИСХОЖДЕНИЕ, а не смысл.** Код проверяет, что
сообщение существует и что оно от клиента (или это предложение владельца
плюс явное согласие). Что сообщение действительно обосновывает пункт — код
судить не может. Поэтому `brief_eval` печатает переписку рядом с брифом:
смотреть должен человек.

**Молчаливый пропуск проверки — худший режим системы**, он выглядит как
успех. Отсюда: неизвестный тип, критерий без обязательного поля и «ни одной
исполнимой проверки» — это провал, а не основание пропустить приёмку.

**Стек выбирает планировщик, но обосновывает ограничениями.** Правило по
умолчанию — самое простое решение. Решение пишется в `docs/DECISIONS.md`
проекта. Раньше здесь стоял блокирующий вопрос клиенту; владелец решил, что
останавливаться не надо, — выбирай сам и объясняй.

## 6. Ловушки, на которые уже наступали

**Фикстуры тихо ломаются от новых обязательных полей.** Схема брифа получила
`priority`, потом `blocking`; задача — `verify_class` и `executor`; проект —
`account_id` (NOT NULL). Каждый раз это роняло либо тесты, либо демо:
`seed_demo` создавал задачи, которые новый гейт не пускал в build, и демо
молча вставало. **Добавляешь обязательное поле — проверь `tests/conftest.py`
и `scripts/seed_demo.py`.**

**heredoc калечит экранирование.** `\n` внутри `<<'PYEOF'` превращался
в настоящий перенос строки прямо посреди f-строки, и файл переставал
парситься. Случалось четырежды за сессию. **Для правок с кавычками и
переносами используй Edit/Write, а не heredoc с python-скриптом внутри.**

**Тесты зависели от времени суток.** Тихие часы 23–9 держат сообщения
клиенту, и половина тестов про отправку была зелёной днём и красной ночью.
Сейчас `QUIET_START=QUIET_END=0` в `tests/conftest.py`.

**Плейсхолдеры из `.env.example` считались валидной настройкой.**
`ANTHROPIC_API_KEY=sk-ant-...` выглядел заданным, код уходил в API и получал
401 вместо внятного «ключа нет». Позже то же повторил `SHEET_ID=1AbC...`.
Лечится `vault._usable()` — используй его для любой новой настройки.

**`INSERT OR IGNORE` в миграции глотает не только дубли.** Он проглотил
`NOT NULL` от колонки, добавленной следующей фазой без `server_default`:
миграция «успешно» перенесла ноль строк. Правила два — булевым колонкам
давать `server_default`, а после переноса явно сверять количества.

**Таймаут оболочки убивает shell, но НЕ Python.** Оборванный на десятой
минуте `brief_eval` пережил SIGTERM, продолжил работать, дописывал строки
в `runs` и жёг квоту — а бриф остался обнулённым, потому что до обработчика
восстановления дело не дошло. Если прогон долгий, запускай в фоне и жди,
а не обрывай. И проверяй `Get-CimInstance Win32_Process`, что не осталось
двух процессов на одном проекте: два `plan_eval` разом пишут задачи через
`_persist` и перемешают план.

**`brief_eval` чистит бриф ПЕРЕД прогоном.** Это by design (полный
пересбор), и при штатном провале он восстанавливает прежнее. При убийстве
процесса — нет. Снимок брифа проекта 8 лежит в `backup/brief8_api.json`.

**`Run.started_at` на самом деле время ОКОНЧАНИЯ** — строка создаётся после
вызова. Мелочь, но она путает разбор длительностей.

**Нечёткое сопоставление нетранзитивно.** Кластеризация пунктов брифа
сравнивала кандидата только с первым элементом группы; A~B и B~C при A≁C
разваливали один пункт на два. Сравнивай со всей группой.

## 7. Как запускать

**Всё через `.venv`.** Системный python падает с `ModuleNotFoundError`.

```bash
# тесты (244 зелёных)
.venv/Scripts/python.exe -m pytest -q

# планировщик вживую, без сети и без трат
.venv/Scripts/python.exe scripts/seed_demo.py
DRY_RUN=1 QUIET_START=0 QUIET_END=0 .venv/Scripts/python.exe -m autopilot.main

# бриф и план по живому проекту 8
.venv/Scripts/python.exe scripts/brief_eval.py --list
.venv/Scripts/python.exe scripts/brief_eval.py --project 8 --samples 1
.venv/Scripts/python.exe scripts/plan_eval.py --project 8

# ручные задачи
.venv/Scripts/python.exe scripts/tasks_cli.py list --project 8
.venv/Scripts/python.exe scripts/tasks_cli.py done 17       # «сделал, проверь»
.venv/Scripts/python.exe scripts/tasks_cli.py confirm 17    # «закрываю под свою ответственность»

# секреты (значения не показываются, кроме get)
.venv/Scripts/python.exe scripts/vault_cli.py list
```

**Прогоны на CLI долгие** (бриф ~4 минуты на прогон, план ~13). Десятиминутный
потолок терминала их не переживёт — запускай в фоне и дожидайся, не обрывая.

### Ключи и токены

Всё в vault (`secrets.enc`, ключ шифрования `VAULT_KEY` в `.env`).
`vault.resolve_secret()` ищет в трёх местах по порядку: vault, окружение,
`.env`, и плейсхолдеры игнорирует.

```
ANTHROPIC_API_KEY   есть (денег на балансе нет — работа идёт по подписке)
QORSA_BOT_TOKEN     есть
HUSTLE_BOT_TOKEN    есть
MAXRU_MAX_TOKEN     НЕТ и взять негде — верификация юрлица РФ
```

`accounts.toml` в `.gitignore` (там id владельца), в репозитории лежит
`accounts.toml.example`.

### Claude Code CLI

Установлен и авторизован, версия 2.1.233. **Запускать надо `claude.exe`,
а не `claude.CMD`** — обёртку `create_subprocess_exec` не исполняет, а через
`cmd.exe` ломается длина командной строки и кодировка. `resolve_cli()` это
делает сам, руками лезть не надо.

```
C:\Users\user\AppData\Roaming\npm\node_modules\@anthropic-ai\claude-code\bin\claude.exe
```

Для `dom` и `screenshot` нужен браузер, он установлен:
`.venv/Scripts/python.exe -m playwright install chromium`.

### Резервные копии

`backup/` (в `.gitignore`). Копию делай **консистентным снимком**, не `cp`:
рядом с базой живёт WAL, и копия одного `.db` теряет незакоммиченное.

```python
src = sqlite3.connect("autopilot.db"); dst = sqlite3.connect("backup/x.db")
with dst: src.backup(dst)
```

## 8. Формат работы

Каждая фаза заканчивается отчётом в чате по одному формату: **что сделал,
что нашёл сверх списка, что осталось сомнительным**. Владелец просил не
сглаживать — плохие новости про качество извлечения ему важнее зелёной
приёмки. Если цифра не измерена, так и говори, а не подгоняй.
